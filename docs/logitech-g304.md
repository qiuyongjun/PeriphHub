# 罗技 G304 / Lightspeed 接收器 046D:C53F —— HID++ 实测笔记

2026-10-31 在本机（Windows 11）实测。鼠标是 G304，2.4G 模式，接收器 product string
为 `USB Receiver`、厂商 `Logitech`。**所有结论都来自真机往返**，未依赖社区文档猜测；
格式对照了 Solaar 的实现（`hidpp20.py` / `common.py`），再用真机数据验证。

## 1. 接口

接收器是复合设备，共 3 个功能（`MI_00` / `MI_01` / `MI_02`），其中 `MI_02` 是厂商集合：

| 集合 | usage page / usage | 报文 | 说明 |
| --- | --- | --- | --- |
| `MI_00` | `0x01` / `0x06` | in 13 | 键盘（接收器兼做键盘接收） |
| `MI_01&COL01` | `0x01` / `0x02` | in 9 | 鼠标 |
| `MI_01&COL02..04` | Consumer / System / `0xFFBC:0x88` | in 2–5 | 多媒体、系统键 |
| `MI_02&COL01` | `0xFF00` / `0x0001` | in 7 / out 7，report id `0x10` | HID++ **short** 通道 |
| `MI_02&COL02` | `0xFF00` / `0x0002` | in 20 / out 20 | HID++ **long** 通道 ⇐ **唯一可用** |
| `MI_02&COL03` | `0xFF00` / `0x0004` | in 32 / out 32 | 用途未知（未使用） |

### 只有长通道能用

在 7 字节的 short 通道上，无论发什么（HID++ 2.0 ping、HID++ 1.0 读寄存器 `0x81`），
接收器一律回 **HID++ 1.0 的 `0x8F` 错误帧**：

```
10 FF 8F 00 00 01 00     # dev=0xFF(接收器), 失败 sub=0x00, 错误 0x01 = 无效 sub-id
10 01 8F 81 07 01 00     # dev=1, 失败 sub=0x81(读寄存器), addr=0x07, 错误 0x01
10 02 8F 81 B5 08 00     # dev=2 未连接 → 错误 0x08 = 不兼容
```

`0x08` 出现在索引 2/3 上，恰好说明**索引 1 是有设备的**，只是不接受寄存器命令。
改用 20 字节长通道（report id `0x11`）后一切正常：

```
11 01 00 00 00 00 01 00   # dev 1, root.getProtocolVersion
```

注意返回的 `swid` 是 `0x00` 而不是发出去的 `0x0A`，所以**匹配应答只能看设备索引
＋功能索引**，不能像标准 HID++ 那样校验 swid。写用 `HidD_SetOutputReport`，
读必须用 `ReadFile`（overlapped），`HidD_GetInputReport` 在该集合上取不到数据。

## 2. 帧格式

```
11  devIdx  featureIdx  (func<<4 | swid)  params[]        # 20 字节，定长
```

应答同构；`featureIdx == 0xFF` 是错误帧：`params[0]` 是出错的功能索引，
`params[1]` 是错误码。本固件把 `swid` 清零返回，见上。

## 3. 实际存在的功能

`root.getFeature(id)` 返回功能索引，**返回 0 就是"这台设备没有这个功能"**（不是错误）：

| feature | 名称 | 索引 | 结论 |
| --- | --- | --- | --- |
| `0x0003` | DEVICE_FW_VERSION | — | 存在，实体数 2 |
| `0x0005` | DEVICE_NAME | — | **存在**，见 §4 |
| `0x1000` | BATTERY_LEVEL_STATUS | `0x05` | **存在**，见 §5 |
| `0x1001` | BATTERY_VOLTAGE | 0 | 不存在 |
| `0x1004` | UNIFIED_BATTERY | 0 | 不存在 |
| `0x1802` | LED_CONTROL | `0x0C` | 存在（本机型无灯） |
| `0x2150` | ADJUSTABLE_REPORT_RATE | 0 | **不存在**；回报率只能走板载配置（§6） |
| `0x2201` | ADJUSTABLE_DPI | `0x1A` | **存在**，改的是"当前 DPI"，见 §6 |
| `0x2202` | POINTER_SPEED | 0 | 不存在 |
| `0x8100` | ONBOARD_PROFILES | `0x07` | **存在且可写**，见 §6 |
| `0x8110` | PER_KEY_LIGHTING | `0x08` | 存在 |
| `0x8060` | MODE_STATUS | `0x09` | 存在 |

## 4. 设备名

`getDeviceNameCount` 返回 **字符串长度**（这台是 37），`getDeviceName(offset)` 返回
从该**字符位置**起的 3 个字节。不是规范里"每 3 字符一块、offset 是块号"的语义，
所以必须按 `offset += 3` 取值，否则会得到 `G3030404 4 L LiLigigh…` 这种叠字。

拼出来是 `G304 Lightspeed Wireless Gaming Mouse`。接收器本身的 product string 只有
`USB Receiver`，所以面板里显示的名字来自这里。

## 5. 电量

`0x1000` function 0 返回 `[level%, levelStatus, chargingStatus, externalPower]`：

```
11 01 05 0A | 1E 14 00 00      # 30%，状态位 0x14，放电中，无外部供电
```

## 6. 板载配置（0x8100）：5 档 DPI + 回报率

这是 G304 上唯一能持久化的地方——`0x2201` 改的是传感器的当前值，断电就回到配置档位。

### 6.1 功能号

| func | 含义 | 参数 |
| --- | --- | --- |
| `0x00` | 取信息 | — |
| `0x50` | 读扇区 | 扇区高、扇区低、偏移高、偏移低 |
| `0x60` | 开始写 | 扇区高、扇区低、0、0、长度高、长度低 |
| `0x70` | 写一块 | 16 字节数据 |
| `0x80` | 提交 | — |

信息回码 `01 03 01 01 01 06 06 00 FF 0A 02` 解析为：存储模型 1、格式 3、
宏格式 1、配置数 1、出厂标志 1、按键数 6、扇区数 6、**扇区大小 `0x00FF` = 255**。

### 6.2 扇区怎么读

255 字节，不是 2 的幂，所以尾部有个坑：

- `0..239`：按 16 字节读，`offset = 0, 16, … 224`；
- 偏移 **240 开始会被拒**（错误帧 `11 01 FF 07 52 02` = 功能 5、swid 2、错误码 2）；
- 最后一段必须读 **239**，返回的 16 字节是 `239..254`，取后 15 字节接到末尾。

### 6.3 控制扇区（扇区 0）

每 4 字节一条：`扇区号(2, 大端) + 启用(1) + 0`，遇到 `FF FF` 结束。这台只有一条：
`sector=1 enabled=1`。

```
000: 00 01 01 00 FF FF 00 00 FF …
0F0: FF … FF 58 7C          ← CRC
```

### 6.4 配置扇区（扇区 1）字段

| 偏移 | 长度 | 含义 | 实测 |
| --- | --- | --- | --- |
| 0 | 1 | 回报率（毫秒） | `01` = 1000 Hz |
| 1 | 1 | 默认档位索引 | `01` |
| 2 | 1 | 侧键切换档索引 | `00` |
| 3 | 10 | 5 档 DPI，各 2 字节**小端** | 400 / 800 / 1600 / 3200 / 0 |
| 13–15 | 3 | RGB | `FF FF FF`（无灯） |
| 16 | 1 | 电源模式 | `FF` |
| 17 | 1 | 直线修正 | `00` |
| 18 | 2 | 写入计数 | |
| 32–96 | 64 | 按键表，每键 4 字节（6 个键） | 默认映射 |
| 160–208 | 48 | 配置名，UTF-16LE | 未设置 |
| 253 | 2 | **CRC16，大端** | `7A 22` |

DPI 是**小端**（`40 06` = 1600），而 `0x2201` 的 DPI 是**大端**（`06 40` = 1600）——
两处字节序相反，写代码时最容易在这里翻车。

### 6.5 校验和

`CRC-16/CCITT-FALSE`（poly `0x1021`，初值 `0xFFFF`），覆盖 `0..252`，结果按**大端**
放在 253–254。用真机数据反推验证过：

| 扇区 | 设备里存的 | 自己算的 |
| --- | --- | --- |
| 控制扇区 0 | `58 7C` | `0x587C` ✅ |
| 配置扇区 1 | `7A 22` | `0x7A22` ✅ |

### 6.6 写入验证过程

1. **空闲扇区 2** 写图案 → 读回逐字节一致 → 再写回全 `FF`，不碰在用配置；
2. 改配置扇区**第 2 档 800 → 900** → 读回 900、CRC 有效；
3. 改回 800 → 读回的整扇区（含 CRC `7A22`）与出厂快照**完全一致**。

### 6.7 一个必须先写配置、后设 DPI 的顺序坑

提交扇区会让固件重新加载当前配置，**把之前用 `0x2201` 设进去的 DPI 覆盖掉**。
所以"切换档位"必须按这个顺序：

```
1. 写配置扇区（默认档索引 = 目标档）
2. setSensorDpi(目标档的 DPI)
3. 回读确认
```

反过来做，表现为"点了档位但指针速度没变"。

### 6.8 当前档位从哪来

配置里的"默认档索引"只在**重新上电**时决定用哪一档；运行中的档位由 `0x2201` 的实时
DPI 反映。鼠标自己的 DPI 键改档时不会改配置，所以面板用"当前 DPI 等于哪一档"来点亮
档位芯片，而不是直接相信默认档索引。

## 7. 还没做的部分

| 项 | 状态 | 原因 |
| --- | --- | --- |
| 按键自定义 / 宏 | 未做 | 按键表格式已知（32 起每键 4 字节），但控制 ID 与任务 ID 的取值表需要逐个试，写错会让按键失灵 |
| 直线修正（角度吸附） | 未开放 | 偏移 17 有对应字节，但无法用肉眼验证是否生效，宁可先不提供开关 |
| LOD / 防抖 / 休眠 | 不可用 | 固件没有对应功能；配置里也没有可确认的字段 |
| 多套配置档 | 未做 | 这台出厂只有 1 条配置（`profileCount=1`），控制扇区也只列了 1 条；虽然扇区表能改，但没有第二份配置可切 |
| 固件升级 | 不做 | 官方独立流程，刷坏即砖 |

## 8. 复现

```bash
cargo run --example hidpp          # 枚举功能、电量、DPI，并 dump 板载扇区（只读）
cargo run --example hidpp -- 1     # 只探测设备索引 1
```

`hidpp` 只读，不会写扇区。运行前关掉面板：两边同时开长通道会互相抢应答。
